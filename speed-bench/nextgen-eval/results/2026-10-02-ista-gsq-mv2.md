# ISTA dense rows: two rows per simdgroup for IQ4_XS, IQ3_S and Q5_K

**Why.** ISTA loses 1.3-1.6 ms per decode step in the GDN stage (`2026-10-02-ista-vs-prod-decode-profile.md`).

| cause | per step | what fixes it |
|---|---|---|
| bytes: ISTA's `attn_qkv`/`attn_gate`/`ssm_out` read 1277 MiB (582 MiB of it Q6_K), against 1114 MiB if all were PROD's Q4_K (+14.6%) | ~0.57 ms | only a weight change |
| kernel: `kernel_qwen4_gsq_mv` ran IQ4_XS, IQ3_S and Q5_K 11-36% slower per byte than PROD's Q4_K kernel; Q6_K was already faster per byte | ~0.68 ms | this change |

The split comes from the SP5 per-type table (2560x24576, T=2 µs/MiB: Q4_K 5.69, Q6_K 5.08, Q5_K 6.30, IQ4_XS 7.21,
IQ3_S 7.75) times ISTA's bytes per type. The sum, 7.59 vs 6.34 ms, matches the measured gap.

**Change.** `kernel_qwen4_gsq_mv2` takes single-output IQ4_XS, IQ3_S and Q5_K rows at 1-8 tokens.
- Two rows per simdgroup share one load of each activation chunk.
- The chunk's scale multiplies the sum of codes once. Q5_K also subtracts its min times the chunk's activation sum.
- The IQ4_XS values and the IQ3_S grid are read from threadgroup memory.
- Codes and scales pass through the runtime zero, as in `gsq_mv`. Q5_K pins both products and their difference,
  because with three terms per update each R1 picked a different fast-math order. That broke the batch-equals-one-token
  check until pinned. A column's sum still does not depend on R1, so MTP verify rows equal one-token rows.
- `DS4_QWEN4_GSQ_MV_ONE_ROW=1` keeps the old kernel for A/B.
- Multi-output calls and every other type keep `gsq_mv`. PROD uses none of these types.

## Kernel level

`ds4_test --metal-kernels` OK:
- The selector picks the new kernel for 13/21/23 with one output at 1-8 tokens, and not for Q6_K, multi-output calls,
  9 tokens or the opt-out.
- Parity against CPU rows at 2560 and 6144 (the `ssm_out` width), 37 rows (an odd last pair).
- Batches of 2/3/6 tokens are bit-identical to one-token rows.
- A swapped IQ4_XS nibble in a scratch shader copy fails all 222 rows. With the opt-out, the old kernel passes parity.

`gsq_bench`, 2560x24576, ms (old -> new), two rounds agree:

|---|---|---|---|---|
| IQ4_XS | 0.171 -> 0.145 | 0.229 -> 0.174 | 0.279 -> 0.220 | 0.650 -> 0.500 |
| IQ3_S | 0.142 -> 0.134 | 0.199 -> 0.166 | 0.251 -> 0.212 | 0.596 -> 0.484 |
| Q5_K | 0.207 -> 0.186 | 0.256 -> 0.214 | 0.297 -> 0.260 | 0.668 -> 0.578 |
| Q6_K (control, unchanged kernel) | 0.222 -> 0.221 | 0.252 -> 0.252 | 0.291 -> 0.292 | 0.664 -> 0.660 |

Per byte at 2 tokens against PROD's Q4_K (5.69 µs/MiB): IQ4_XS 5.46 and Q5_K 5.2-5.4 meet it; IQ3_S 6.44 does not (-17%).

**Expected per decode step (2-token verify), from the microbench (measured below: +4.1% with MTP):**
- GDN projections: about 0.7 ms.
- The Q5_K output head (437 MB, through `qwen4_gemv`): about 0.4 ms more.
- The remaining GDN gap to PROD is the Q6_K bytes (~0.57 ms).

## End to end

GPU window 14:50-15:08 on 2026-10-02, gateway paused (`backend_ok` again 15:11). Script
`ds4-metal-data/sp3gemm/run-mv2-e2e.sh`, ISTA IQ3_XXS hc-F16. "old" is `DS4_QWEN4_GSQ_MV_ONE_ROW=1`.

**Correctness**
- **GPU vs CPU, 31 tokens:** old worst 3.098 with top-1 30/31; new the same, 3.098 and 30/31.
- **PROD greedy, 3 prompts:** identical to the develop-tree outputs. PROD's dense types never reach the multi-gemv
  entry, so no PROD speed A/B was run.
- **Greedy with MTP against without (new kernel):** prompts 2 and 3 identical. Prompt 1 splits at character 345 of 411
  on a near-tie ("# Check odd divisors" vs "if n == 3:"); both read correctly.
  - This is the known effect from SP5 (`2026-10-01-sp5-gsq-verify.md`): some verify-path component outside the gemv
    (attention, GDN, MoE or the mixed fused groups) is not R1-invariant, and the near-tie it flips moves when the
    numerics move.
  - The new kernel's verify columns are bit-equal at kernel level.

**Perplexity**, average NLL per token, old -> new:

| text | old | new |
|---|---|---|
| en | 0.58726 | 0.58788 |
| code | 0.02056 | 0.02291 |
| vi | 1.19832 | 1.19654 |
| en-new | 2.08801 | 2.09331 |
| code-new | 0.74217 | 0.73507 |
| vi-new | 2.04397 | 2.04742 |

- Three texts move up and three down. The mean over the six moves +0.08%.
- Code's +0.0024 is 4.8 nats over 2048 tokens: a few tokens, on a text the model predicts almost perfectly.
- This is rounding-level movement, not a quality change.

**Speed**
- **ds4-bench, 8K prompt, 128 tokens, no MTP, two rounds with the order swapped:** decode old 33.13 / 33.61, new
  33.96 / 34.00 t/s (+1.8%). Prefill unchanged.
- **With MTP, `ds4 --mtp`, 256 tokens, one run each:**

  | prompt | old | new | change |
  |---|---|---|---|
  | prime | 45.70 t/s | 47.05 t/s | +3.0% |
  | blue sky (VI) | 40.82 t/s | 42.85 t/s | +5.0% |
  | TCP/UDP | 41.91 t/s | 43.74 t/s | +4.4% |

  Draft acceptance is unchanged (98.0/80.0/85.0% vs 96.1/80.0/84.3%).
- The MTP gain is larger because MTP verifies at 2 tokens, where the kernel gains most.
