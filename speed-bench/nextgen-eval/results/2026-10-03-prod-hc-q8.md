# PROD with Q8_0 hc projections: no gain once page-cache warmth is controlled

Overnight 2026-10-02/03. The user granted autonomy to run the three Strata levers, share GPU time with the Ornith
and DS41F sessions, and report in the morning. No push and no deploy were done.

**Verdict:** the lever is dropped. Its branch `feature/prod-hc-q8` was deleted unmerged on 2026-10-03, and only
this note reached develop.
- An early 3-round A/B showed prefill +40% and decode +8%. That was a page-cache artifact: PROD's runs were cold
  and the Q8 file's were warm.
- With each file run twice back to back and the warm second runs compared:
  - prefill is −1.3% for the Q8 file + opt-in;
  - steady decode is +0.7%;
  - perplexity on the prefill GEMM path is +0.3%.

## The three Strata levers (window Q1)

| lever | measured | outcome |
|---|---|---|
| PLE as batched GEMMs | the PLE group is 41-48 ms of ~4.9 s GPU per 2048-token chunk (0.9%) | dropped: <1% possible |
| PLE read-ahead | n-gram gather 15-27 ms per 5.5 s chunk (0.35%), already 16-way parallel | dropped |
| split hc norm per token and stream | `kernel_qwen4_hc_norm` is already split by token × stream × 8 chunks | already in ds4 |
| FP8 KV as default | +0.07% ppl vs f16 against q4's +0.91% (2026-10-02 note); costs +1.6 GiB at 262K, +3.3 GiB at 512K | not pursued |

The qwen4 startup "planned" memory line is the same for the q4, fp8 and f16 KV modes (52.52 GiB at 262K), so it
cannot size them. The real buffers are q4 0.5 B, fp8 1 B and f16 2 B per element (ds4.c:60227).

## The hc lever that looked real

The Q1 decode profile showed the hc down GEMV and gate-mix at 15% of GPU time, reading ~1.2 GB of F16 projections
per step. The branch built a test for it. None of this code is in develop:

| part | what |
|---|---|
| tool | `tools/gguf_hc_to_q8.py`: ggml-reference Q8_0 for hc `{attn,ffn}_{down,up}`, nextn `hc_head`, `output_hc` |
| runtime opt-in | `DS4_QWEN4_HC_Q8_GEMM=1`: a Q8_0 hc up takes the prefill GEMM path (default: per-token gate-mix) |
| tests | a bound for that path |
| review fixes | refuse non-finite weights; pin tie rounding and multi-block bytes; exact verify rows (PLD span) keep the gate-mix |

The test file was PROD's hc projections in Q8_0: 51.07 GiB, 614 MB smaller than PROD, local only and deleted
afterwards.

The ds4 runtime already accepts Q8_0 hc weights (ds4.c qwen4_graph_weights_supported). The conversion is a
straightforward per-32-value Q8_0 rewrite of those tensors, if anyone needs it again.

### Measurements

ds4-bench at 8K with 128 generated tokens. Prefill in t/s:

| run | PROD | Q8 file + opt-in |
|---|---|---|
| Q2/Q3, interleaved rounds | 317.6 / 323.7 / 333.9 | 441.6 / 430.0 / 492.8 |
| **Q4, warm second run of a back-to-back pair** | **452.5 / 440.9** | **446.0 / 435.8** |
| Q4, first (cold) run of a pair | 327.1 / 335.1 | 370.8 / 429.7* |

\* q8g-b1 directly followed q8g-a2, so its pages were already warm.

Steady decode, Q4 warm: PROD 28.86 / 28.74, Q8 + opt-in 29.06 / 28.98 (+0.7%).

**Why the Q2/Q3 rounds misled.** A PROD run that follows another file starts on a cold page cache: prefill drops
to ~330 t/s from ~445 warm. In Q2/Q3, every PROD run followed a Q8-file run or another session's window, while the
Q8 runs often followed each other. The reviewer flagged that the Q2/Q3 gains could not be explained by the stage
profile. Q4 confirmed it.

**Without the opt-in,** the Q8 file sends prefill through the per-token gate-mix: 181-184 t/s, −43%.

**Decode stages**, SUB_TS, normalised to the unchanged GDN qkv GEMV:
- the hc down GEMV is about −25%;
- the Q8 gate-mix kernel is about +12%. It has no M5 register-prefetch variant, unlike F16.
- Net, hc is about −6%, which matches the +0.7% end to end.

**Kernel tests.**
- The Q8_0 up GEMM path is within 2e-4 of the double reference on the kernels production picks: 1.7e-4 on the
  generic matmul at T=16, and 2.7e-7 on batch_mm at T=16.
- The test harness's down step uses the generic matmul at T=16/24 and drifts to rel 2-3e-4 there. Production sends
  those row counts to batch_mm or dense_mm.

## Lessons for later A/Bs on PROD

- **Control page-cache warmth.** Run each arm twice back to back and compare the second runs, or flush between
  arms. Two 52 GB files cannot both stay warm on a 64 GB machine.
- **The cold-vs-warm gap is itself a user-facing number.** PROD's 8K prefill is ~330 t/s cold and ~445 t/s warm
  (+35%). When the gateway serves Ornith and then switches to Qwen, Qwen's first prefills run cold. A file warm-up
  when the Qwen row starts (for example `madvise(WILLNEED)` on the resident trunk) is a candidate lever for
  time-to-first-token. It has not been built or measured.
