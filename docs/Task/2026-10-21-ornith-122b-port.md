# Ornith-1.5-122B → ds4 qwen35moe second shape (M5 Pro 64 GB) Implementation Plan

> **For agentic workers:** implement task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run `ornith-ai/Ornith-1.5-122B` (arch `qwen35moe`, llama.cpp dialect) on the ds4 engine's existing Ornith-1.5-35B-A3B graph by adding a second shape profile (48 trunk + 1 MTP layers, n_embd 3072, 32 heads, 256 experts top-8, ff 1024, GDN v-heads 64) and loading an engine-conformed GGUF. Target machine: M5 Pro 64 GB unified, ~350 GB free disk. First file: `unsloth/Ornith-1.5-122B-GGUF` Q4_K_M (75.84 GB, mmap-streamed); second tier: an IQ2-recipe resident artifact built from it with `gguf-tools`.

**Architecture:** All qwen35moe support already exists on `develop` (a71725fb): shape-table-driven graph (`ds4_qwen35moe.inc`), type-generic MoE kernels (`qwen35_row_dot` → `qwen4_row_dot` covers Q2_K/IQ2_XXS/Q4_K/Q5_K/Q6_K/MXFP4…), args-driven attention/GDN/MTP pipelines, fp8/q4 KV modes, llama.cpp-dialect validator (`qwen35moe.*` keys) and binder (`weights_bind_qwen35moe_layer` matches the 122B tensor names exactly, including the fused output gate folded into a 2×`q_dim` `attn_q`). The 122B differs from the 35B only in dimensional fields, so the port is: second `ds4_shape` profile + shape dispatch by `qwen35moe.embedding_length` + widening the dense qtype gate with `Q6_K` (unsloth Q4_K_M embeds `output.with` Q6_K). No new kernels.

**Tech Stack:** C (ds4.c single-file engine), Objective-C (ds4_metal.m), Python 3.9+ (gguf-tools), Metal 3. Existing Makefile builds; existing real-model tests.

**Spec:** Header-verified evidence (this session):
- unsloth `Ornith-1.5-122B-UD-IQ2_XXS.gguf` header: arch `qwen35moe`, block_count 49 (48 trunk + nextn 1), embedding 3072, head 32 / kv 2 / key 256 / value 256, rope 10 MHz base, dim_count 64, experts 256 top-8 ff 1024 shared ff 1024, ssm conv 4 / state 128 / group 16 / time_step_rank 64 / inner 8192, full_attention_interval 4, context 262144.
- Tensor names per layer match `weights_bind_qwen35moe_layer` exactly: full-attn layers have `attn_q [3072, 16384]` (2×q_dim fused output gate — engine already expects this at `weights_validate_qwen35moe_layout`), `attn_k/v [*, 512]`, `attn_output`, `q_norm/k_norm [256]`; GDN layers have `attn_qkv [3072, 12288]`, `attn_gate [3072, 8192]`, `ssm_a`/`ssm_dt.bias [64]`, `ssm_conv1d [4, 12288]`, `ssm_alpha/beta [3072, 64]`, `ssm_norm [128]`, `ssm_out [8192, 3072]`; MTP block (blk.48) has `nextn.eh_proj [6144, 3072]`, `nextn.enorm/hnorm/shared_head_norm [3072]`.
- No hc_*/PLE/indexer tensors — matches the 35B contract (the qwen35 validator never asks for them).
- The ds4 GGUF type table matches llama.cpp's 2026 enum exactly (16 IQ2_XXS, 17 IQ2_XS, 18 IQ3_XXS, 19 IQ1_S, 20 IQ4_NL, 21 IQ3_S, 22 IQ2_S, 23 IQ4_XS, 29 IQ1_M, 30 BF16) — no id remap needed.
- The dense gate (`tensor_type_is_qwen4_dense`) already accepts the whole GSQ-RCO set (Q3_K/Q5_0/Q5_K/Q6_K/Q2_0 + IQ2_XS/IQ2_S/IQ3_XXS/IQ3_S/IQ4_NL/IQ4_XS) on top of Q8_0/F16/F32/BF16/Q4_0/Q4_K — unsloth UD dense rows pass as-is; no dense change was needed (test pins Q6_K).
- True qwen35 quant blockers: (a) `tensor_expect_qwen35_expert_layout` hard-requires Q4_K/Q5_K stacked experts ("use the 23G or 25G tier" error text) — satisfied by the official `ornith-ai` Q4_K_M file, NOT by unsloth UD mixes; (b) `qwen4_expert_row_bytes` (ds4_metal.m) returns 0 for IQ1_S (19) and IQ1_M (29), and CPU ref `qwen4_ref_row` + Metal `qwen4_row_dot` don't decode them — unsloth UD-IQ2_XXS carries 21 IQ1_S stacked tensors. Phase 3's own IQ2-tier artifact avoids IQ1 entirely, so only (a) needs widening.
